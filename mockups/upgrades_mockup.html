How it would work

  • Upgrades live on a budget line. Each line (e.g. Windows and doors) can have any number of upgrades: name, extra price, Yes/No, who asked (Buyer / Builder), status and a note.
  • Yes adds the price, No doesn’t. Line total = base budget + upgrades set to Yes. Category totals, tiles and the build cost all use the line total. No upgrades are kept as a record but add $0.
  • Status is optional detail. Switching to Yes marks a Quoted upgrade Approved; picking Declined switches it to No. Quoted + Yes is allowed (counts now, price may change).
  • Over / under compares invoices with the line total, so an approved upgrade explains an overage instead of showing it as a cost overrun.
  • Per version. Upgrades are saved in the version being edited. “New version” copies them; older versions keep theirs. Comparing versions shows upgrade changes.
  • Projected final cost = per line, the larger of line total and invoices (Done lines use invoices).
  • Done marker moves to its own narrow first column: one tap on the circle; hover “Done ⓘ” for what it means.
  • Show upgrades switch: off gives today’s compact table, with the budget column showing the line total and “incl. +$ upgrades”.

Open questions for you

  • Should declined upgrades be kept (greyed, struck through) or deleted? Mockup keeps them.
  • Should a Quoted upgrade set to Yes count in the totals, or only Approved ones?
  • Are buyer upgrades charged to the buyer? If yes, should they raise the sale price on the project (Inputs tab) as well as the build cost, and show as a separate line in the investor report?
  • Do you need a printable upgrade summary for the buyer (change orders with sign-off date)?
  • Should invoices be linkable to a specific upgrade, or only to the line?
  • Is “Requested by: Buyer / Builder” enough, or do you want a markup % on buyer upgrades?
  • Which layout do you prefer: A (inline), B (side panel) or C (one list of all upgrades)? C can be added on top of A or B.
